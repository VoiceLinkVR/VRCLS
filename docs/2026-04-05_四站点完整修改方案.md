# 2026-04-05 四站点完整修改方案

## 1. 目标

将当前官网体系明确拆分为四类站点：

1. 产品介绍站
2. 用户控制台站
3. 服务状态站
4. 管理员站

本方案的目标不是做“概念上的拆分”，而是给出一套可落地的修改方案，覆盖：

- 信息架构
- 域名与路径规划
- 仓库目录与构建方式
- 前后端边界
- 与客户端联动
- 部署方案
- 迁移步骤

---

## 2. 总体决策

## 2.1 推荐方案

推荐采用：

- 逻辑上四站点
- 物理上同一主域名、按路径部署
- 同一官网仓库统一构建产物

推荐路径如下：

- `/`：产品介绍站
- `/app/`：用户控制台站
- `/status/`：服务状态站
- `/admin/`：管理员站

推荐 API 路径如下：

- `/auth/*`：用户认证接口
- `/api/*`：用户控制台业务接口
- `/manageapi/*` 或 `/adminapi/*`：管理员接口
- `/status-probe/*`：状态采集接口

## 2.2 为什么不用四个独立子域名

现阶段不建议一开始拆成：

- `www.xxx.com`
- `account.xxx.com`
- `status.xxx.com`
- `admin.xxx.com`

原因：

- 你当前系统规模不大，路径拆分已经足够清晰
- 同域路径部署可以大幅降低 Cookie、CORS、反向代理和证书复杂度
- 可以最大程度兼容当前 `portal`、`status`、`admin` 的现有结构
- 后续真要拆子域名，也可以在路径方案稳定后再迁移

结论：

- 现在先按“四类站点”做逻辑隔离
- 不急着做“四套完全独立基础设施”

## 3. 四站点定义

## 3.1 产品介绍站

定位：

- 对外展示产品价值
- 承担下载入口
- 承担用户教育和转化

建议页面：

- `/`
- `/download`
- `/pricing`
- `/docs`
- `/faq`

核心内容：

- VRCLS 是什么
- 支持什么场景
- 客户端下载
- 价格和套餐说明
- 常见问题
- 引导去用户控制台和状态站

不应该承载：

- 登录后业务操作
- 订单管理
- 账户安全设置
- 管理后台入口

## 3.2 用户控制台站

定位：

- 面向普通用户的登录后站点
- 负责账户、订单、配额、计费和安全设置

建议路径：

- `/app/`

建议页面：

- `/app/auth`
- `/app/overview`
- `/app/security`
- `/app/email`
- `/app/orders`
- `/app/billing`
- `/app/usage`

可扩展页面：

- `/app/reset-password`
- `/app/verify-email`
- `/app/sessions`

核心内容：

- 登录/注册
- 当前套餐
- 当前剩余资源
- 订单列表
- 支付入口
- 修改密码
- 绑定邮箱

不应该承载：

- 管理员功能
- 服务探测逻辑
- 产品宣传内容

## 3.3 服务状态站

定位：

- 面向公开访客的运行状态展示页
- 展示平台整体健康度和历史事件

建议路径：

- `/status/`

核心内容：

- Overall 状态
- 各服务节点状态
- 事件记录
- 最近更新时间

建议数据来源：

- `/status-probe/api/status/public`
- `/status-probe/api/status/refresh`

不应该承载：

- 用户登录
- 订单或计费
- 管理操作

## 3.4 管理员站

定位：

- 面向内部管理员
- 管理用户、订单、系统状态和运营动作

建议路径：

- `/admin/`

核心内容：

- 管理员登录
- 用户管理
- 订单管理
- 手动补单
- 运营统计
- 风险控制

不应该承载：

- 普通用户自助页面
- 对外产品宣传页面

## 4. 路径与权限边界

| 区域 | 路径 | 访问权限 | 说明 |
| --- | --- | --- | --- |
| 产品介绍站 | `/`、`/download`、`/pricing` | 公开 | SEO 友好、静态内容优先 |
| 用户控制台站 | `/app/*` | 用户登录后 | SPA |
| 服务状态站 | `/status/*` | 公开 | 静态页 + 状态 API |
| 管理员站 | `/admin/*` | 管理员登录后 | SPA |
| 用户认证 | `/auth/*` | 公开/登录态混合 | 普通用户认证 |
| 用户业务 API | `/api/*` | 用户登录后 | 控制台业务接口 |
| 管理 API | `/manageapi/*` | 管理员登录后 | 管理后台接口 |
| 状态探测 API | `/status-probe/*` | 公开只读 | 状态页接口 |

关键原则：

- 普通用户和管理员认证状态分离
- `/auth/*` 不给管理员站复用为唯一入口
- `/manageapi/*` 不向普通用户站暴露
- 状态页永远保持匿名可访问

## 5. 仓库与目录改造方案

## 5.1 当前问题

当前仓库已经存在：

- 根目录静态页
- `portal/`
- `status/`
- `admin/`
- `.deploy-site/`
- `deploy-site.tar`

问题是：

- 源码和部署产物混在一起
- 构建基准路径不统一
- `.deploy-site/` 看起来像手工产物，不像受控构建输出

## 5.2 目标目录结构

建议改造成：

```text
vrclswebsite/
  docs/
  sites/
    product/
    portal/
    status/
    admin/
  shared/
    assets/
    brand/
  scripts/
    build-all.ps1
    pack-deploy.ps1
    sync-deploy.ps1
  dist-sites/
    product/
    app/
    status/
    admin/
  README.md
```

如果你希望少动现有目录，也可以先走过渡方案：

```text
vrclswebsite/
  assets/
  status/
  portal/
  admin/
  scripts/
  dist-sites/
```

过渡期建议：

- 保留 `portal/`、`admin/`、`status/`
- 新增 `scripts/`
- 新增统一输出目录 `dist-sites/`
- 停止把 `.deploy-site/` 当成手工维护目录

## 5.3 构建产物唯一真相

后续必须明确：

- 所有发布文件只从 `dist-sites/` 生成
- `.deploy-site/` 不再手工编辑
- `deploy-site.tar` 只由脚本打包生成

这一步是全方案里最优先的工程治理动作。

## 6. 前端技术方案

## 6.1 产品介绍站

推荐方案：

- 继续做静态站
- 但纳入统一构建体系

可选实现：

1. 继续保留纯 HTML/CSS/JS
2. 改造成 Vite 静态项目

推荐选择：

- 短期保留静态实现
- 中期纳入 `sites/product` 统一构建

原因：

- 产品站主要是内容页
- 不需要复杂状态管理
- 重点是稳定发布和 SEO

## 6.2 用户控制台站

推荐方案：

- 保持 `Vue 3 + Vite + TypeScript + Vue Router + Pinia`

原因：

- 当前 `portal/` 已经是这套栈
- 成本最低
- 足够承载控制台复杂度

必须调整的点：

- 统一 `base` 为 `/app/`
- 路由按 `/app/` 运行
- 解决 SPA 刷新回退

## 6.3 服务状态站

推荐方案：

- 保持静态前端
- 不要为了状态页引入完整 SPA 框架

原因：

- 状态页本质是公开数据展示页
- 页面简单
- 只需要稳定读取状态接口

## 6.4 管理员站

推荐方案：

- 保持 `Vue 3 + Vite + TypeScript`

必须调整的点：

- 保持独立基准路径 `/admin/`
- 与普通用户控制台样式和认证边界分开

## 7. 后端接口分工方案

## 7.1 用户控制台接口

归属：

- `VoiceLinkServer1`

继续使用或补齐：

- `POST /auth/register`
- `POST /auth/login`
- `POST /auth/logout`
- `GET /auth/me`
- `GET /api/account/profile`
- `GET /api/account/entitlements`
- `GET /api/account/orders`
- `GET /api/account/usage`
- `POST /api/account/change-password`
- `POST /api/account/bind-email`
- `POST /api/account/verify-email`
- `POST /api/account/forgot-password`
- `POST /api/account/reset-password`
- `GET /api/billing/guide`
- `GET /api/billing/plans`
- `POST /api/billing/order-intents`
- `GET /api/billing/order-intents/{id}`

## 7.2 管理员接口

继续独立：

- `/manageapi/*`
- 或统一为 `/adminapi/*`

建议：

- 最好择一
- 不要长期同时维护两套语义重复前缀

如果当前后台已大量依赖 `/manageapi/*`，则短期保留，后续再整理。

## 7.3 状态采集接口

有两个方案：

### 方案 A：保留独立状态探测服务

优点：

- 状态页与主后端解耦
- 不影响主业务 API

缺点：

- 多一个进程
- 多一份部署配置

### 方案 B：并入 `VoiceLinkServer1`

优点：

- 统一部署
- 统一日志和鉴权边界

缺点：

- 主后端承担额外状态探测职责

推荐：

- 短期保留独立 `status-probe`
- 中期视部署复杂度决定是否并回主后端

## 8. 与客户端的联动修改方案

## 8.1 下载入口统一

当前问题：

- 官网下载按钮指向 GitHub 仓库
- 客户端实际更新链路在对象存储/CDN

建议：

- 产品介绍站的下载页只展示正式分发入口
- 不再把 GitHub 仓库当成默认下载入口

下载页至少要展示：

- 当前稳定版版本号
- 安装包下载按钮
- 更新时间
- 更新说明入口
- 系统要求

## 8.2 用户控制台与客户端关系

建议边界：

- 客户端负责“登录并使用服务”
- 复杂账户管理迁移到用户控制台

客户端保留：

- 登录
- 查看基础权益
- 打开官网控制台

客户端逐步弱化：

- 复杂发电/充值入口
- 订单全流程管理
- 账户安全操作

## 8.3 版本发布链路

建议产品站下载页读取正式发布源，而不是手写链接。

可选数据源：

- `appcast.xml`
- 发布清单 JSON
- 后端包装后的 release API

推荐：

- 先加一个轻量 release manifest JSON
- 产品站下载页读取这个 manifest
- 客户端更新和官网展示共用同一发布真相

## 9. 部署方案

## 9.1 Nginx 路由建议

推荐最终形态：

```nginx
location / {
  try_files $uri $uri/ /index.html;
}

location /app/ {
  try_files $uri $uri/ /app/index.html;
}

location /status/ {
  try_files $uri $uri/ /status/index.html;
}

location /admin/ {
  try_files $uri $uri/ /admin/index.html;
}

location /auth/ {
  proxy_pass http://127.0.0.1:9001;
}

location /api/ {
  proxy_pass http://127.0.0.1:9001;
}

location /manageapi/ {
  proxy_pass http://127.0.0.1:9001;
}

location /status-probe/ {
  proxy_pass http://127.0.0.1:8787;
}
```

注意：

- `/app/` 和 `/admin/` 必须有 SPA fallback
- `/status/` 原则上可以纯静态
- `/auth/` 和 `/api/` 建议与控制台同域，避免复杂 CORS

## 9.2 发布流程建议

统一发布流程：

1. 构建 `product`
2. 构建 `portal`
3. 构建 `admin`
4. 拷贝 `status`
5. 生成 `dist-sites/`
6. 打包成部署压缩包
7. 上传服务器
8. 切换软链接或原子替换目录

禁止继续使用：

- 手动复制零散文件上线
- 人工修改 `.deploy-site/` 后直接打包

## 10. 分阶段实施方案

## Phase 0：先统一部署真相

目标：

- 消除源码与产物漂移
- 明确四站点的唯一部署输出

要做的事：

- 新增 `scripts/build-all.ps1`
- 统一产物目录到 `dist-sites/`
- 停止手工维护 `.deploy-site/`
- 统一 `portal` 和 `admin` 的 `base`
- 修复根首页对 `/app/` 的断链

验收标准：

- 本地一条命令可生成完整四站点产物
- 生成结果可直接部署

## Phase 1：产品介绍站整理

目标：

- 把产品站从“Demo 首页”整理成正式入口

要做的事：

- 新增下载页
- 新增定价说明页
- 清理与控制台混杂的链接文案
- 把控制台入口统一指向 `/app/`
- 下载入口改成正式分发源

验收标准：

- 产品站不再依赖 GitHub 仓库链接充当主下载入口

## Phase 2：用户控制台站补齐

目标：

- 让 `portal` 成为真正可用的账户中心

要做的事：

- 固定 `base: '/app/'`
- 修复深链刷新
- 补齐邮箱、改密、找回密码、重置密码页面
- 接上 `/api/billing/plans`
- 统一登录后布局和错误处理

验收标准：

- 普通用户可以在浏览器中完成账户主要操作闭环

## Phase 3：服务状态站正式化

目标：

- 让状态页脱离 Demo 性质

要做的事：

- 明确状态 API 的正式部署方式
- 默认配置不再在纯静态预览下直接失败
- 增加降级策略
- 明确状态来源说明

验收标准：

- 状态页在无 API 时可展示受控降级结果
- 在有 API 时正常实时刷新

## Phase 4：管理员站硬隔离

目标：

- 让管理员站成为独立内控界面

要做的事：

- 统一 `/admin/` 基准路径
- 明确仅管理员可访问
- 整理 `/manageapi` 或 `/adminapi` 前缀
- 加强登录态边界

验收标准：

- 管理员站不与普通用户站共用混乱入口

## Phase 5：客户端联动切换

目标：

- 把复杂账户操作从桌面客户端迁移到控制台站

要做的事：

- 客户端增加“打开控制台”入口
- 弱化客户端内复杂运营页
- 官网下载页接正式版本发布源

验收标准：

- 用户对账户和订单的主要操作在官网完成

## 11. 关键工程要求

## 11.1 必须统一编码和文档

当前仓库已有明显编码显示混乱现象。后续必须：

- 统一 Markdown、HTML、JS、TS、JSON 为 UTF-8
- 明确编辑器和构建工具编码约定
- 修正文档与真实配置不一致的问题

## 11.2 必须统一命名

建议统一：

- 用户控制台叫“控制台”或“用户控制台”
- 路径继续使用 `/app/`
- 不要再混用 `portal`、`app`、`control panel` 多套对外称呼

管理员站同理：

- 对内可叫 Admin
- 对外路径固定 `/admin/`

## 11.3 必须统一发布配置来源

至少统一三类真相：

1. 前端基准路径
2. API 根路径
3. 客户端下载/更新源

## 12. 最终推荐结论

最终推荐的完整落地方案是：

- 保持一个官网仓库
- 在一个主域名下运行四类站点
- 产品站走 `/`
- 用户控制台走 `/app/`
- 服务状态站走 `/status/`
- 管理员站走 `/admin/`
- 用户认证和业务接口继续由 `VoiceLinkServer1` 提供
- 状态采集接口走 `/status-probe/`
- 所有站点统一由脚本构建到 `dist-sites/`
- 先解决部署和路径问题，再补齐控制台功能，再整理下载与客户端联动

这是当前阶段最稳、改造成本最低、又能支撑后续继续演进的方案。
