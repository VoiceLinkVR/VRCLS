# 2026-03-09 用户中心发电流程优化方案

> 基于原始方案的评审结果，针对 5 个关键问题给出改进建议。

---

## 一、问题清单与优化对照表

| # | 原方案问题 | 影响 | 优化措施 |
|---|----------|------|---------|
| 1 | `upgrade` 语义不明：是永久升档还是临时 boost？ | 后端有 `limit_rule`(永久) 和 `boost_limit_rule`(临时) 两套，方案未区分 | 统一为永久升档，废弃 boost 概念 |
| 2 | User 模型缺少 `plan_price`，需从 `limit_rule` 反推价格 | `AFDIAN_BOOST_DAILY_INCREMENT` 变更时历史数据反推出错 | User 新增 `plan_price` 字段 |
| 3 | `payment-guide` 每次传明文密码 | 增加密码泄露面，正式用户体验差 | 区分"自己发电"与"代他人发电"两种模式 |
| 4 | `renew_option.readonly` 冗余 | `min == max` 已隐含不可修改 | 删除 `readonly` 字段 |
| 5 | "禁用额度"概念模糊 | 方案多次提及但未定义 | 明确定义并固化为后端内部逻辑 |

## 二、优化 1：统一 upgrade 语义，废弃 boost

### 2.1 现状分析

后端 User 模型有两套额度体系：

```
limit_rule          = "1500/day"    # 永久基础额度
boost_limit_rule    = "3000/day"    # 临时提升额度
boost_expiration_date               # 临时提升过期时间
```

现有 `payment-link` 的 ACTION_ALIASES：

```python
# user_center.py:22-27
ACTION_ALIASES = {
    "renew_1m": "renew",
    "boost_1m": "upgrade",
    "renew":    "renew",
    "upgrade":  "upgrade",
}
```

但实际 activate 逻辑中，`upgrade` 执行的是**永久升档**（修改 `limit_rule`，清空 `boost_*`）：

```python
# user_center.py:397-414 (activate 中的 upgrade 分支)
user.limit_rule = _build_limit_rule_for_plan(...)  # 永久修改
user.boost_expiration_date = None                   # 清空 boost
user.boost_limit_rule = None                        # 清空 boost
```

### 2.2 结论

`upgrade` 实际上已经是永久升档。`boost_*` 字段在当前 activate 流程中只会被清空，从未被写入新值。

### 2.3 优化方案

- **明确：`upgrade` = 永久升档**，activate 时修改 `limit_rule`
- **`boost_*` 字段保留但不再新增写入**，仅作为历史兼容（已有 boost 用户自然过期）
- `payment-guide` 和 `payment-link` 中只支持三种 action：`renew` / `upgrade` / `downgrade`
- 删除 `boost_1m` 别名

### 2.4 对 `dependencies.py` 的影响

`get_effective_user_limit_rule()` 函数仍保留——已有 boost 未过期的用户仍能享受 boost 额度直到自然过期。无需改动。

## 三、优化 2：User 模型新增 `plan_price` 字段

### 3.1 问题复现

当前反推价格的函数：

```python
# user_center.py:163-169
def _calculate_price_from_daily_limit(daily_limit):
    # daily_limit=3000, increment=1500 -> units=2 -> price=10
    # 如果 increment 改成 2000 -> units=1 -> price=5  (错误!)
```

如果 `AFDIAN_BOOST_DAILY_INCREMENT` 从 1500 改成 2000，所有历史用户的"当前档位"反推都会出错。

### 3.2 数据库变更

```sql
ALTER TABLE user ADD COLUMN plan_price FLOAT DEFAULT NULL;
```

对应 models.py：

```python
class User(Base):
    # ... 现有字段
    plan_price = Column(Float, nullable=True)  # 用户购买时的月价，如 5.0, 10.0
```

### 3.3 数据迁移

对已有用户，执行一次性迁移脚本，用**当前** increment 值反推并写入：

```python
# 一次性迁移脚本（在 increment 还是 1500 时执行）
for user in all_users:
    user.plan_price = _infer_plan_price_from_rule(user.limit_rule)
db.commit()
```

### 3.4 写入时机

- `activate` 中 renew/upgrade/downgrade 成功后，写入 `user.plan_price = plan_price`
- `payment-guide` 读取时，直接用 `user.plan_price`，不再反推

### 3.5 向后兼容

`_infer_plan_price_from_rule()` 函数保留作为 fallback：

```python
def get_user_plan_price(user: User) -> float:
    if user.plan_price is not None:
        return user.plan_price
    # fallback: 旧用户未迁移时仍可反推
    return _infer_plan_price_from_rule(user.limit_rule)
```

## 四、优化 3：区分鉴权模式，减少密码传输

### 4.1 两种发电场景

| 场景 | 说明 | 鉴权方式 |
|------|------|---------|
| 自己发电 | 当前登录的正式账户给自己续费/升级 | JWT Token（已有） |
| 代他人发电 | 测试账户登录后，为正式账号发电 | 目标账号的 username + password |

### 4.2 接口设计优化

```
POST /api/user-center/payment-guide
```

**请求字段（二选一鉴权）：**

```json
{
  // 模式 A：JWT 鉴权（自己发电），Header 带 Authorization: Bearer <token>
  // 不需要 username/password 字段

  // 模式 B：密码鉴权（代他人发电）
  "username": "target_user",
  "password": "target_password"
}
```

**后端逻辑：**

```python
@router.post("/payment-guide")
async def payment_guide(
    payload: Optional[PaymentGuideRequest] = None,
    current_user: Optional[User] = Depends(get_current_user_optional),
    db: Session = Depends(get_db),
):
    if payload and payload.username and payload.password:
        # 模式 B：密码鉴权，验证目标账号
        target_user = authenticate_target(db, payload.username, payload.password)
    elif current_user and not _is_test_user(current_user.username):
        # 模式 A：JWT 鉴权，为自己发电
        target_user = current_user
    else:
        raise HTTPException(400, "请提供正式账号密码或使用正式账号登录")

    return build_guide_response(target_user)
```

### 4.3 前端交互优化

```
正式账户登录 -> 自动调用 payment-guide（JWT鉴权，无需输入密码）
                -> 直接展示续费/升级选项

测试账户登录 -> 显示"请填写正式账号密码"
              -> 用户输入后，调用 payment-guide（密码鉴权）
              -> 展示续费/升级/降档选项
```

**好处**：正式用户 0 次额外密码输入，体验大幅提升。

## 五、优化 4：精简响应字段

### 5.1 删除冗余字段

| 删除字段 | 理由 |
|---------|------|
| `renew_option.readonly` | `min == max` 已隐含；前端判断 `min === max` 即可锁定 |
| `anchor_reason` | 调试信息不应暴露给前端，改为后端日志输出 |

### 5.2 优化后的响应结构

```json
{

  "is_expired": true,
  "status": "expired",

  "current_plan": {
    "plan_price": 10,

    "allowed": true,

    "max_price": 10,
    "step": 5,

  },
  "upgrade_option": {
    "allowed": true,
    "default_price": 15,
    "min_price": 15,
    "max_price": 100,
    "step": 5,
    "preview_daily_quota": 4500
  },
  "downgrade_option": {
```

### 5.3 关键变更说明

1. **`current_plan` 替代 `display_*` 散落字段**——语义更清晰，前端取值更方便
2. **`preview_daily_quota` 替代 `target_resource_quota_preview`**——名字更短，含义一致
3. **`plan_price` 替代 `monthly_price`**——与 User 模型字段名一致，减少概念映射
4. **`downgrade_option.max_price`**——当用户是 20 元档时，`max_price` 应为 15（低于当前档的最高值），不是固定 5

## 六、优化 5：明确"禁用额度"定义

### 6.1 现有代码行为

查看后端代码，`is_active=False` 的用户：
- 登录时被拦截（`api.py:94-96`）
- `limit_rule` **不会被清空或修改**
- `expiration_date` **不会被修改**

所以"禁用额度"就是：**被管理员手动禁用（`is_active=False`）的用户，其 `limit_rule` 和 `plan_price` 仍保留原值**。

### 6.2 在 payment-guide 中的处理

```python
def build_guide_response(user: User) -> dict:
    # 1. 即使 is_active=False，也读取 plan_price 作为"当前档位"
    # 2. 因为用户可能先被禁用、后被重新激活并发电
    # 3. 这个判断只在后端做，前端不需要知道"禁用额度"的存在

    plan_price = get_user_plan_price(user)  # 包含禁用用户的历史档位
    # ... 后续计算 allowed_actions, options 等
```

### 6.3 文档口径

> "禁用额度"指被管理员禁用的用户其历史购买档位。该档位在计算升级/降档边界时参与计算，确保用户重新激活后的档位判断准确。此逻辑仅在后端执行，前端无需感知。

## 七、guide_token 实现方案

### 7.1 复用现有 Fernet 加密

后端已有 `afdian_service.build_custom_id()` / `parse_custom_id()` 基于 Fernet 的加解密机制。guide_token 可直接复用：

```python
def build_guide_token(username: str, plan_price: float, allowed_actions: list) -> str:
    payload = {
        "v": 2,                          # 版本号，区分 custom_id(v=1)
        "username": username,
        "plan_price": plan_price,
        "allowed_actions": allowed_actions,
        "ts": int(time.time()),
        "nonce": uuid.uuid4().hex[:16],
    }
    return afdian_service._fernet.encrypt(
        json.dumps(payload, ensure_ascii=False, separators=(",", ":")).encode()
    ).decode()


def verify_guide_token(token: str, max_age_seconds: int = 300) -> dict:
    payload = afdian_service.parse_custom_id(token)  # 复用解密
    if payload.get("v") != 2:
        raise ValueError("invalid guide token version")
    ts = payload.get("ts", 0)
    if int(time.time()) - ts > max_age_seconds:
        raise ValueError("guide token expired")
    return payload
```

### 7.2 不需要额外存储

- guide_token 是自包含的加密令牌，无需存 Redis 或数据库
- 5 分钟有效期通过 `ts` 字段 + 解密时校验实现
- 与现有 `custom_id` 共用同一个 Fernet key

## 八、payment-link 接口改造

### 8.1 新增 guide_token 参数

```python
class PaymentLinkRequest(BaseModel):
    username: str = Field(..., min_length=3, max_length=50)
    password: str = Field(..., min_length=6, max_length=100)
    action: str = Field("renew")
    months: int = Field(1, ge=1, le=24)
    plan_price: Optional[float] = None
    custom_price: Optional[float] = None
    guide_token: Optional[str] = None  # 新增：来自 payment-guide 的令牌
```

### 8.2 校验逻辑

```python
@router.post("/payment-link")
async def create_payment_link(payload: PaymentLinkRequest, db: Session = Depends(get_db)):
    action = _normalize_action(payload.action)

    # 如果携带 guide_token，进行复核
    if payload.guide_token:
        guide = verify_guide_token(payload.guide_token)
        if guide["username"] != payload.username:
            raise HTTPException(400, detail="PAYMENT_GUIDE_ACCOUNT_STATE_CHANGED")
        if action not in guide.get("allowed_actions", []):
            raise HTTPException(400, detail="PAYMENT_GUIDE_ACTION_NOT_ALLOWED")

    # ... 后续逻辑保持不变
```

### 8.3 向后兼容

`guide_token` 为 Optional，旧客户端不传也能正常工作。新客户端传了则做额外校验。逐步切换，无需一次性强制升级。

## 九、downgrade 逻辑详细设计

### 9.1 允许条件

```python
def is_downgrade_allowed(user: User) -> bool:
    # 仅已过期用户允许降档
    expired, _ = is_user_expired(user)
    return expired
```

### 9.2 降档范围计算

```python
def get_downgrade_range(current_plan_price: float) -> dict:
    step = settings.AFDIAN_BOOST_PRICE_STEP       # 5
    increment = settings.AFDIAN_BOOST_DAILY_INCREMENT  # 1500
    min_price = step                                # 最低 5 元
    max_price = current_plan_price - step           # 低于当前档一级

    if max_price < min_price:
        # 当前已经是最低档，不允许降档
        return {"allowed": False}

    return {
        "allowed": True,
        "default_price": min_price,
        "min_price": min_price,
        "max_price": max_price,
        "step": step,
        "preview_daily_quota": int(min_price / step) * increment,
    }
```

### 9.3 activate 中的 downgrade 处理

```python
# 在 activate 的 action 分支中新增 downgrade
elif action == "downgrade":
    if not is_downgrade_allowed(user):
        raise HTTPException(400, detail="账户未过期，不允许降档")
    if plan_price >= current_price - PRICE_EPSILON:
        raise HTTPException(400, detail="降档价格必须低于当前档位")

    extend_days = int(settings.AFDIAN_RENEW_DAYS) * months
    user.expiration_date = _extend_date(None, extend_days)  # 从当前时间开始
    user.limit_rule = _build_limit_rule_for_plan(user.limit_rule, plan_price)
    user.plan_price = plan_price
    user.boost_expiration_date = None
    user.boost_limit_rule = None
    user.is_active = True
```

## 十二、与原方案差异总结

| 项目 | 原方案 | 优化方案 |
|------|--------|---------|
| upgrade 语义 | 未说明 | 明确为永久升档，废弃 boost 写入 |
| 当前档位获取 | 从 limit_rule 反推 | User.plan_price 直接存储 |
| payment-guide 鉴权 | 始终传 username+password | JWT(自己) / password(代他人) 双模式 |
| `readonly` 字段 | 有 | 删除，用 `min==max` 替代 |
| `anchor_reason` 字段 | 有 | 删除，改为后端日志 |
| 响应中的 `display_*` 字段 | 散落多个字段 | 收归 `current_plan` 对象 |
| downgrade 范围 | 示例只写 min=max=5 | 明确 max = current_price - step |
| "禁用额度"定义 | 模糊 | 明确定义 + 文档口径 |
| `ACCOUNT_DISABLED` 错误码 | 无 | 新增 |
| guide_token 实现 | 未说明 | 复用 Fernet，自包含令牌，无需存储 |
| 向后兼容 | 未考虑 | guide_token Optional，旧客户端不受影响 |
