# VRCLS 公开状态页设计说明

## 1. 目标

状态页的目标是公开展示开发者服务器当前是否可用，而不是暴露内部运维细节。

因此设计上强调：

- 简洁
- 面向普通用户可读
- 支持公开访问
- 数据结构稳定，方便后续接入真实监控

## 2. 信息架构

状态页分为三部分：

### 2.1 总体状态

展示：

- 当前整体状态：`Operational / Degraded / Outage`
- 一句话说明
- 最后刷新时间
- 平均延迟
- 最近 30 天可用率

### 2.2 服务明细

每个服务卡片展示：

- 服务名称
- 服务描述
- 当前状态
- 区域
- 延迟
- 最近 30 天可用率
- 最后检查时间
- 公开地址或说明

### 2.3 事件列表

展示最近的公开事件：

- 标题
- 影响等级
- 开始时间 / 恢复时间
- 修复过程更新

## 3. 为什么前后端分离

因为官网要放在 GitHub Pages，而 GitHub Pages 不能运行动态后端。

所以最合适的结构是：

- `github.io` 托管首页和状态页前端
- 你的服务器托管状态 API
- 前端通过 CORS 去拿状态数据

优点：

- 发布简单
- 成本低
- 状态 API 可独立演进
- 将来切换监控实现时，前端不需要大改

## 4. API 数据结构

当前 Demo 使用如下结构：

```json
{
  "updatedAt": "2026-03-10T00:30:00+08:00",
  "overall": {
    "title": "VRCLS 开发者服务状态",
    "message": "当前核心服务均可用。",
    "status": "operational",
    "uptime30d": 99.93
  },
  "services": [],
  "incidents": []
}
```

含义：

- `overall.status`：页面顶部总状态
- `services`：服务卡片列表
- `incidents`：事件时间线

## 5. 状态等级定义建议

### operational

- 所有关键服务可用
- 对普通用户无明显影响

### degraded

- 服务可用但有性能下降
- 或非关键服务不可用

### outage

- 核心服务不可用
- 用户主要功能受阻

## 6. 对外公开时的注意事项

建议只公开必要信息，不要公开：

- 内网 IP
- 数据库名称
- 私有节点详细拓扑
- 实际服务器登录信息
- 过度详细的错误堆栈

公开状态页更像是“用户可见健康信息”，不是内部监控后台。

## 7. 当前 Demo 的后续升级方向

- 接入真实健康检查接口
- 对接 PM2 / systemd / Docker 容器状态
- 增加历史可用率统计
- 增加维护公告与计划维护窗口
- 增加 Telegram / Discord / 邮件通知
