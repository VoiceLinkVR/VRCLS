# 2026-04-05 官网项目问题梳理

## 范围

本次检查覆盖以下目录：

- 官网仓库：`D:\git\gitlab\vrclswebsite`
- 后端仓库：`D:\git\gitlab\VoiceLinkServer1`
- 客户端仓库：`D:\git\gitlab\VRCLS-CSharp`

目标不是做 UI 美化建议，而是确认当前官网项目在实际交付、部署和与后端/客户端联动时存在的真实问题。

## 检查方式

- 读取官网根目录、`portal/`、`admin/`、`status/`、`.deploy-site/`、`status-api-demo/` 的源码和构建产物
- 对 `portal` 和 `admin` 执行 `npm run build`
- 对静态 JS 执行 `node --check`
- 用本地静态服务器验证关键路径是否可访问
- 核对官网前端与后端 `portal_api`、客户端更新配置之间的契约

## 结论概览

当前项目的主要问题不在“代码编译不过”，而在“源码、部署产物、文档、后端能力之间已经出现明显漂移”。  
最核心的几个风险是：

1. 官网首页当前直接指向 `app/`，但当前仓库根目录并没有这个路径，入口在本地预览下直接失效。
2. `portal` 源码构建出来的是根路径版本，但真正部署产物 `.deploy-site/app` 却是 `/app/` 版本，已经形成双套真相。
3. 账号中心使用 `createWebHistory()`，但当前仓库没有 SPA 回退配置，深链刷新会 404。
4. 后端已经提供找回密码、重置密码、绑邮箱、验证邮箱等能力，但官网前端并没有实现这些页面和流程。
5. 状态页默认配置依赖 `/status-probe` 反向代理，而当前仓库提供的本地预览方式并不会提供这个接口，开箱即失败。

## 与后端、客户端的联动判断

### 1. 官网与后端

官网 `portal` 现有已接通的能力主要是：

- `/auth/register`
- `/auth/login`
- `/auth/logout`
- `/auth/me`
- `/api/account/profile`
- `/api/account/entitlements`
- `/api/account/orders`
- `/api/account/usage`
- `/api/billing/guide`
- `/api/billing/order-intents`

这一层契约基本对得上，说明“登录后概览/订单/用量/充值”主路径已经能成立。

但以下能力已经在后端存在、官网仍未接：

- 修改密码
- 绑定邮箱
- 验证邮箱
- 忘记密码
- 重置密码
- 账单计划列表 `/api/billing/plans`

结论：后端账号体系已经明显先走了一步，官网前端仍停留在 MVP。

### 2. 官网与客户端

客户端当前关注两类地址：

- 业务 API：通过 `BaseUrl` / `ApiIp` / `ApiPort` 指向后端 `/api/*`
- 程序更新：通过 `UpdateServerUrl` / `AppUpdateFeedUrl` 指向对象存储/CDN

官网目前没有与客户端发布链路建立可验证的一致性：

- 官网下载按钮仍是 GitHub 仓库链接
- 官网没有读取 `appcast.xml` 或任何版本清单
- 官网没有展示“当前稳定版”“安装包体积”“更新时间”“更新日志”

结论：官网目前更像“介绍页 + portal 入口”，还不是“客户端正式分发入口”。

## 建议优先级

### P0：先统一发布真相

- 明确唯一正式部署目录，例如只保留 `.deploy-site/`
- 增加一个一键构建脚本，把根站点、`portal`、`admin` 统一打包到同一目录
- 删除或停用会误导人的重复产物目录

### P1：修掉线上会直接炸的路径问题

- 修正首页和状态页的 `app/` 入口策略
- 统一 `portal` 的 `base` 配置与实际部署路径
- 为 `/app/*` 增加 SPA fallback，或者改回 hash 路由

### P1：补齐账号体系闭环

- 落地 `/verify-email`
- 落地 `/forgot-password`
- 落地 `/reset-password`
- 落地修改密码与绑定邮箱页面
- 校正后端返回的 `nextUrl` 与前端真实路由

### P2：整理文档与对外下载入口

- 更新 README、`portal/README.md`、`docs/03-部署说明.md`
- 删除失效描述，例如未使用的 `VITE_API_BASE_URL`
- 决定官网下载页到底要跳 GitHub、对象存储安装包，还是“最新稳定版”页面

## 最后判断

当前项目不是“不能继续做”，而是已经进入一个典型的“能跑，但发布方式和产品边界不再清晰”的阶段。  
如果现在直接继续加功能，不先统一构建和部署约定，后面每次发布都会越来越依赖人工经验，风险会持续上升。
