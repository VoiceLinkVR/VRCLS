1. 当前生产后端实际上仍运行在 `legacy mode`

- `v1` 是否继续开放，由显式配置控制

## 3. 核心设计决策

## 3.1 标识体系最终结论

这里有两个容易冲突的说法：

- “用户名都以 id 为准”
- “以后都采用 uuid 作为用户标识”

为了避免设计自相矛盾，本方案统一解释为：

1. 数据库内部继续保留自增 `id` 作为主键，主要用于排序和关联
2. 对外唯一用户标识改为 `user_uuid`
3. `username` 进入兼容期，仅用于旧逻辑兼容，不再作为新体系主标识
4. 新用户注册时不再输入用户名，不再输入昵称
5. 新用户展示名默认取“用户 + 短 UUID”或“用户 ID”，但这只是展示字段，不是认证字段
6. 登录凭证统一为：
   - 邮箱 + 密码
   - 或控制台设备授权登录
7. token、订单、日志、配额、加油包、账户安全等系统间引用，逐步从 `username` 切换为 `user_uuid`

结论：

- `id` 是数据库内部主键
- `user_uuid` 是业务唯一标识
- `username` 只做兼容，不再做新体系核心字段

## 3.2 迁移原则

你这次给出的新思路更合理，应该从“全量兼容旧 API”改成“新站点/新 API 独立，旧体系只保留迁移入口和 self-host 能力”。

新的迁移原则如下：

1. 官网控制台和新接口作为 `v2`
2. 旧客户端密码体系和旧接口作为 `v1`
3. `v2` 不去完整兼容 `v1` 的业务语义
4. `v1` 中与旧支付/旧发电格式强绑定的接口，默认关闭或仅保留兼容开关
5. 旧用户进入新站点时，可以继续用“旧用户名 + 旧密码”登录一次
6. 但登录成功后必须立刻进入邮箱绑定/升级流程，转入 `v2` 身份体系
7. self-host / 自定义后端继续保留旧密码认证路线，不强制切 `v2`

这意味着：

- 新网站可以是全新的用户入口
- 新 API 可以是全新的业务接口
- 不需要为了新站点把旧 API 逻辑全部背进来
- 旧体系只保留：
  - 迁移入口
  - self-host 兼容入口
  - 明确受控的 `v1 compat` 开关

### v1 / v2 总体分工

#### v1

- 面向旧客户端和 self-host
- 保留旧用户名/密码认证
- 保留 legacy 计费解释
- 旧格式发电/支付接口默认关闭，必要时通过配置放开

#### v2

- 面向新网站和新控制台
- 主登录方式为邮箱 + 密码 / 控制台授权登录
- 用户主身份为 `user_uuid`
- 采用新的计费与账户安全体系
- 不强制兼容旧发电接口格式

## 5. 默认测试账户方案

## 5.1 目标

必须保留一个默认测试账户，并且这个测试账户不靠手工初始化，不靠运营人员记忆，不靠数据库里“碰巧有一条 testuser”。

这里进一步明确：

- 这个默认测试账户不是给用户拿去登录的正式账号
- 它对应的是“用户没有注册、没有登录时，客户端默认落到的匿名公共试用身份”
- 用户不能在控制台、客户端、API 上主动以这个测试账户名义登录
- 它本质上是一个受控的匿名兜底账户，而不是普通用户账户

## 5.2 推荐方案

新增一组明确配置：

```env
DEFAULT_TEST_USER_ENABLED=True
DEFAULT_TEST_USER_UUID=00000000-0000-0000-0000-000000000001
DEFAULT_TEST_USER_EMAIL=test@voicelinkvr.top
DEFAULT_TEST_USER_PASSWORD=ChangeMe123!
DEFAULT_TEST_USER_DISPLAY_NAME=Public Test User
DEFAULT_TEST_USER_DAILY_QUOTA=800
DEFAULT_TEST_USER_RATE_LIMIT=8/minute
DEFAULT_TEST_USER_RESOURCE_QUOTA=0
DEFAULT_TEST_USER_ACTIVE=True
```

服务端启动时执行“默认测试账户自愈逻辑”：

1. 开机检查该 `DEFAULT_TEST_USER_UUID` 是否存在
2. 不存在则自动创建
3. 存在则按配置补齐缺失字段
4. 默认不要每次覆盖邮箱和密码，避免运维误改被强行冲回
5. 配额规则和限速规则允许按配置更新

客户端和服务端的行为约束应补充为：

1. 客户端未登录时，默认使用该匿名测试账户的配额与限速策略
2. 该账户不出现在普通登录页、控制台登录页、公开注册页
3. 认证接口不允许用户直接以该测试账户邮箱/用户名登录
4. 控制台中不提供该账户的普通用户资料页
5. 管理后台中要明确标记该账户为“匿名测试账户”，避免误当成真实用户运营

## 5.3 配额与限速必须分开配置

测试账户的两类限制必须独立：

1. 额度限制
   - 每日额度
   - 资源余额
   - 加油包可用性
2. 限速限制
   - 每分钟请求数
   - 必要时后续支持每 10 秒或每小时限制

推荐不要再只靠 `LIMIT_PUBLIC_TEST_USER=testuser` 这种字符串判断。

应该改为：

- 通过 `DEFAULT_TEST_USER_UUID` 标识默认测试账户
- 用户对象上增加 `is_default_test_user`
- 限流、配额、展示逻辑都以该标志位和配置为准

额外约束：

- `is_default_test_user = true` 的账户不允许走普通登录
- 该账户的 session/token 只允许由系统匿名兜底逻辑生成，不允许用户主动申请
- 所有匿名试用请求在日志中应标识为“default_test_user”或等价字段，便于和真实用户流量分离

关于匿名测试账户的限制口径，这里明确采用“策略归属默认测试账户、实际统计按 IP 分桶”的方案：

1. 匿名测试账户的限流维度按 `IP` 执行
2. 不改成“按匿名测试账户用户名限流”
3. 匿名试用额度桶也按 `IP` 统计
4. 不改成“全站共享一个匿名测试账户额度桶”
5. 即：
   - 策略归属上，它落到默认测试账户
   - 速率限制上，它按当前访客 IP 计算
   - 匿名试用额度上，它也按当前访客 IP 计算
6. 这样可以保持现有匿名访问的防滥用能力，不会因为统一映射到一个默认测试账户而把所有未登录用户混进同一个限流桶或额度桶

建议实现口径：

- 策略模板：`default_test_user`
- 限流键：`anonymous_ip:{client_ip}`
- 匿名额度键：`anonymous_quota:{client_ip}:{utc_day}`
- 日志标签：
  - `actor_type = anonymous_test`
  - `user_uuid = DEFAULT_TEST_USER_UUID`
  - `rate_limit_scope = ip`
  - `quota_scope = ip`

## 6. 计费与档位配置化方案

## 6.1 当前问题

当前计费体系已经部分配置化，但仍有明显硬编码残留：

- 默认价格阶梯写死在 `plan_catalog`
- 资源增量依赖固定步长推导
- 测试账户规则混在普通用户逻辑里
- 加油包价格和资源增量虽可配置，但还是“单步长推算”，表达能力不够

## 6.2 本轮目标

改成“完整配置驱动”的方案：

1. 免费档可配置
2. 默认测试档可配置
3. 正式付费档数组可配置
4. 加油包数组可配置
5. 每档金额、每日额度、资源额度、限速规则均可单独定义
6. 新旧档位可兼容解析

## 6.4 关键决策

1. 正式付费档继续按“金额阶梯”展示
2. 但不再假设“每 5 元一个固定资源步长”
3. 每个档位的价格、每日额度、限速完全由配置定义
4. 加油包也不再只靠“步长乘法”，而是支持显式配置多个包
5. 若需要兼容旧行为，可以保留“缺省推导逻辑”，但只作为 fallback

## 6.5 旧配置兼容

为兼容现网旧库和旧部署，建议支持两种模式：

### 兼容模式

- 如果没有 `version: 2` 的完整配置
- 则服务端按旧逻辑推导

### 新模式

- 如果检测到 `version: 2`
- 则完全按显式配置解析

## 7. 数据库迁移方案

## 7.1 User 表新增字段

建议新增：

- `user_uuid CHAR(36) UNIQUE NOT NULL`
- `is_default_test_user BOOLEAN NOT NULL DEFAULT 0`
- `display_name VARCHAR(100) NULL`
- 可选：`identity_version INT NOT NULL DEFAULT 1`

如要支持“邮箱账号绑定旧账号密码”，还建议增加一张映射/归并记录表，例如：

- `user_identity_link`

建议字段：

- `id`
- `user_uuid`
- `legacy_user_id`
- `legacy_username`
- `link_type` (`legacy_password_bind`)
- `linked_at`
- `linked_by_ip`
- `status`

说明：

- `user_uuid` 是后续所有对外身份主键
- `identity_version` 用于区分旧账号和新账号迁移阶段

## 7.2 关联表新增字段

以下表建议逐步补 `user_uuid`：

1. `account_token`
2. `request_log`
3. `payment_order`
4. 后续若有 `entitlement`、`quota_history`、`device_authorization` 的扩展表，也应补齐

推荐迁移方式：

- 先加可空字段 `user_uuid`
- 根据 `username -> user.user_uuid` 回填历史数据
- 新写入路径同时写 `username` 和 `user_uuid`
- 稳定后再逐步把 `user_uuid` 提升为主检索字段

## 7.3 旧库升级步骤

推荐启动期自动升级按以下顺序：

1. `user` 表新增 `user_uuid`
2. 为旧用户生成 UUID 并回填
3. `user` 表新增 `is_default_test_user`
4. `payment_order` 新增 `user_uuid`
5. `request_log` 新增 `user_uuid`
6. `account_token` 新增 `user_uuid`
7. 给新增字段加索引
8. 执行一次性数据回填
9. 执行默认测试账户自愈创建

## 7.4 旧用户兼容策略

旧用户迁移时：

1. 保留原 `username`
2. 为每个旧用户生成稳定 `user_uuid`
3. 登录后统一返回 `user_uuid`
4. 前端不再展示和依赖旧 `username`
5. 支付、订单、管理后台暂时允许同时展示：
   - `user_uuid`
   - 旧 `username`
   - 邮箱

这样不会影响现网旧用户继续使用。

如果用户不是自动迁移，而是后续手工在控制台完成“绑定旧账号密码”，则要支持：

1. 先创建新的邮箱用户
2. 再把旧账户身份挂到这个邮箱用户下
3. 后台与日志中保留可追溯的绑定记录

## 8. 认证与账户体系改造方案

## 8.1 注册

新注册流程改为：

1. 用户输入邮箱
2. 用户输入密码
3. 用户输入邮箱验证码
4. 不再要求昵称
5. 服务端创建账号时自动生成：
   - `id`
   - `user_uuid`
   - 默认展示名
   - 默认免费档权益

服务端请求模型建议调整：

- 删除 `display_name` 必填
- 若前端仍传该字段，也只做可选备用字段

## 8.2 登录

新体系登录方式：

1. 邮箱 + 密码
2. 控制台授权登录
3. 旧用户名 + 旧密码登录，但仅作为迁移入口

不再推荐：

- 用户自己记“用户名 + 密码”登录

这里要改成更明确的产品策略：

1. 新站点允许老用户继续用旧用户名 + 旧密码登录
2. 但这不是长期并行主登录方式，而是“迁移入口”
3. 老用户一旦通过旧用户名登录成功，系统立即要求：
   - 绑定邮箱
   - 完成邮箱验证
   - 升级为 `v2` 账户身份
4. 完成升级后，站点主推登录方式切换为：
   - 邮箱 + 密码
   - 控制台授权登录
5. 若用户拒绝绑定邮箱，则只允许停留在受限迁移态，不开放完整 `v2` 能力

建议前端登录模式明确展示为：

1. 邮箱登录
2. 控制台授权登录
3. 旧账号迁移登录

补充一条兼容思路：

### 邮箱登录后绑定旧账号密码

这个想法是合理的，而且很适合作为旧体系过渡桥梁。

但现在要调整优先级：

1. 首选迁移路径不再是“先邮箱注册，再绑定旧账号”
2. 首选迁移路径改为“旧用户名 + 旧密码先登录新站点，再强制绑定邮箱”
3. “邮箱登录后绑定旧账号密码”保留为补充入口
4. 它适用于：
   - 用户已经先创建了新的邮箱账号
   - 后续才想把旧账号资产并过来
   - 管理员协助用户做二次归并

推荐设计为：

1. 用户先通过邮箱体系注册或登录控制台
2. 在控制台进入“绑定旧账号”页面
3. 用户输入旧体系里的：
   - 旧账号
   - 旧密码
4. 服务端校验旧账号密码成功后，把旧账号关联到当前邮箱用户
5. 绑定完成后，旧账号的历史权益、订单、额度、日志归并到当前 `user_uuid`

这样做的价值：

1. 老用户不需要先理解 UUID 迁移
2. 老用户可以直接用自己记得的旧账号密码完成身份归并
3. 新体系依然以邮箱和 `user_uuid` 为主，不需要长期保留旧账号登录入口

但必须加上这些限制：

1. 一个旧账号只能绑定到一个新的 `user_uuid`
2. 绑定动作必须在用户已登录邮箱账号的前提下进行
3. 绑定完成后应记录：
   - 绑定时间
   - 旧用户名
   - 旧用户 id
   - 新 `user_uuid`
4. 如果旧账号本身已经绑定过邮箱用户，禁止重复绑定
5. 如发现目标双方都有订单、额度或加油包，必须定义清晰的合并规则，不能直接隐式覆盖

### 旧账号绑定的合并规则

这部分本轮直接定死，后续编码按这个规则执行，不再临场发挥。

#### 规则 A：目标用户是谁

1. 以“当前已登录的邮箱用户”为唯一目标账号
2. 旧账号不能反向覆盖邮箱用户
3. 绑定完成后，目标账号的主身份仍然是当前邮箱用户的 `user_uuid`

#### 规则 B：身份字段怎么处理

1. 保留目标邮箱用户的：
   - `user_uuid`
   - 邮箱
   - 邮箱验证状态
   - 当前密码
2. 旧账号的 `username`、旧 `id`、旧密码只进入映射记录，不覆盖新账号主身份
3. 若旧账号原本没有邮箱，则直接挂为历史身份
4. 若旧账号已有邮箱但未验证，可作为历史字段保留，不覆盖当前邮箱
5. 若旧账号已有且已验证邮箱，并且与当前登录邮箱不同，则默认禁止自动合并，进入人工处理或管理员审批

#### 规则 C：订单怎么合并

1. `payment_order` 的归属统一迁到当前邮箱用户的 `user_uuid`
2. 历史 `username` 字段保留，作为审计信息，不立即清空
3. 所有待支付、已支付、已激活、已取消订单都保留原状态，不因绑定而改状态
4. 订单时间线不重写，只改归属关系
5. 若同一外部订单已经同时挂在两边，禁止重复迁移，按订单唯一键去重

#### 规则 D：套餐与有效期怎么合并

1. 若旧账号有有效订阅，当前邮箱账号无有效订阅：
   - 直接把旧账号订阅迁到当前邮箱账号
2. 若两边都有有效订阅：
   - 取“到期时间更晚”的那条作为当前生效订阅
   - 另一条订阅进入 `merged_subscription_snapshot` 审计记录
   - 不做自动叠月，避免错误放大权益
3. 若两边都无有效订阅：
   - 保持当前邮箱账号现状
4. 当前生效的 `limit_rule / plan_id / expiration_date` 以合并后的最终结果回写到目标账号

#### 规则 E：每日额度怎么合并

1. 每日额度不做“数值相加”
2. 每日额度属于“当前生效套餐属性”，应跟随最终保留的主订阅
3. 如果两边套餐不同，按规则 D 选出来的主订阅决定每日额度和限速
4. 防止通过账号绑定把两份日额度叠成一份更大的日额度

#### 规则 F：加油包怎么合并

1. 加油包余额可以相加
2. 加油包总购买量可以相加
3. 加油包过期时间取“更晚的有效过期时间”
4. 若一边加油包已过期，先按现有清理规则清掉过期余额，再参与合并
5. 合并后要记录：
   - 合并前双方余额
   - 合并后余额
   - 合并前双方过期时间
   - 合并后过期时间

#### 规则 G：请求日志和配额统计怎么处理

1. 历史 `request_log` 不回写重算当日已消耗额度
2. 历史日志保留原始 `username / user_uuid / ip`
3. 新绑定完成后的新请求都记到目标邮箱账号的 `user_uuid`
4. 不因为绑定而追溯重算过去几天的消耗量，避免审计口径混乱

#### 规则 H：会话和 token 怎么处理

1. 旧账号现有 session、refresh token、设备授权状态全部失效
2. 当前邮箱账号保留当前会话
3. 若绑定成功后需要更干净，可要求当前邮箱账号重新签发一次 access token / refresh token
4. 这样可以避免旧账号继续拿历史 token 独立活动

#### 规则 I：冲突和禁止条件

以下情况直接禁止自动绑定：

1. 旧账号已绑定到别的 `user_uuid`
2. 旧账号是默认测试账户
3. 旧账号是管理员账号
4. 旧账号与当前账号邮箱冲突且旧邮箱已验证
5. 检测到订单唯一键、支付归属、订阅快照存在不可判定冲突

#### 规则 J：绑定完成后的账号状态

1. 旧账号标记为 `merged` 或等价状态
2. 旧账号不再允许独立密码登录
3. 旧账号不再参与正常套餐、额度、订单查询
4. 旧账号只作为历史身份记录保留
5. 当前邮箱账号成为唯一对外可用账号

## 8.3 Token 负载

当前 token 中大量使用：

- `sub = username`
- `uid = id`

建议改为：

```json
{
  "sub": "user_uuid",
  "uid": 123,
  "legacy_username": "old_name",
  "sid": "session_id",
  "type": "access"
}
```

解释：

- `sub` 迁移为 `user_uuid`
- `uid` 继续放内部数值主键，方便后台排查
- `legacy_username` 只在兼容期保留

## 8.4 控制台授权登录

该方向继续保留，并进一步强化为推荐登录方式。

客户端文档继续参考：

- [2026-04-06_控制台授权登录接入说明](D:\git\gitlab\VRCLS-CSharp\docs\2026-04-06_控制台授权登录接入说明.md)

本轮控制台与服务端需要做的补充是：

1. 授权记录返回 `user_uuid`
2. token 中 `sub` 改为 `user_uuid`
3. 客户端后续持久化以 `user_uuid` 为账户键
4. 控制台授权页上不再强调旧用户名

## 9. 前端控制台修改方案

页面行为建议：

1. 用户输入旧用户名 + 旧密码

3. 跳转地址建议：`/app/auth?mode=login`
4. 跳转时附带邮箱参数可选：`/app/auth?mode=login&email=...`

## 9.3 用户信息展示

前端后续不再以 `username` 作为主展示字段。

控制台建议显示优先级：

1. `displayName`

不再显示：

- 老式登录用户名作为主标题

## 9.4 状态页

## 9.5 旧账号绑定页

- `/app/link-legacy-account`

页面职责：

1. 已登录邮箱用户输入旧账号和旧密码

3. 展示待合并的旧账户摘要

## 10.1 API 版本策略

建议从这轮开始把接口分层说清楚：

### v1

- 旧客户端相关接口
- 旧用户名/密码认证
- legacy 计费与旧发电逻辑
- self-host / 自定义后端优先继续用这一层

### v2

- 新网站控制台接口
- 邮箱登录、邮箱验证、控制台授权登录
- 新计费体系、新套餐展示、新安全能力
- 用户主身份统一为 `user_uuid`

### 关键策略

1. 新网站默认只对接 `v2`
2. 只有“旧账号迁移登录”这个入口允许读 `v1` 身份信息
3. 旧格式发电接口默认关闭
4. 通过显式配置决定是否继续开放 `v1` 兼容能力

建议配置项：

```env
API_V1_ENABLED=True
API_V1_PAYMENT_ENABLED=False
API_V1_LEGACY_LOGIN_ENABLED=True
API_V2_ENABLED=True
API_V2_BILLING_ENABLED=False
```

解释：

- `API_V1_ENABLED`：是否保留旧接口整体可用
- `API_V1_PAYMENT_ENABLED`：是否继续开放旧格式发电/支付
- `API_V1_LEGACY_LOGIN_ENABLED`：是否允许旧用户名迁移登录
- `API_V2_ENABLED`：是否开放新站点接口
- `API_V2_BILLING_ENABLED`：是否正式开放新计费体系

现有 `custom_id` 里大量包含 `username` 和历史密码语义。

建议下一轮开始：

3. 激活成功后把 `payment_order.user_uuid` 回写完整

根据你这次的新判断，旧格式发电接口不应该再被当成新网站正式能力。

1. `v1` 发电接口默认关闭
2. 只在以下场景通过配置放开：
   - self-host
   - 私有部署
   - 明确需要兼容旧客户端的特殊实例
3. 新网站控制台不再直接接旧格式发电接口
4. 新网站只接 `v2` 订单与计费接口
5. 当前生产由于仍是 legacy 模式，可保持：
   - `v1` 认证可用
   - `v1` 发电默认不对新站点开放
   - `v2` 计费先灰度，不直接正式开放

## 19. 老用户迁移登录流程

## 19.1 目标

老用户进入新网站时，体验应该是：

1. 我还能用旧用户名 + 旧密码进来
2. 进来以后马上完成邮箱升级
3. 升级完成后就转成新账号体系

而不是：

1. 先让用户理解一堆版本差异
2. 再自己决定该用哪个登录入口

## 19.2 推荐流程

### 路径 A：旧账号迁移登录

1. 用户进入新网站 `/app/auth`
2. 选择“旧账号迁移登录”
3. 输入旧用户名 + 旧密码
4. 服务端校验 legacy 身份成功
5. 返回迁移态登录结果：
   - `migration_required = true`
   - `email_bound = false | true`
   - `email_verified = false | true`
6. 前端根据结果分支：
   - 未绑定邮箱：跳转绑定邮箱
   - 已绑定未验证：跳转邮箱验证
   - 已绑定且已验证：直接完成升级
7. 升级完成后：
   - 生成/确认 `user_uuid`
   - 签发 v2 session / token
   - 提示用户后续改用邮箱登录

### 路径 B：邮箱先注册，再绑定旧账号

1. 用户先走邮箱注册
2. 登录控制台
3. 进入“绑定旧账号”
4. 输入旧用户名 + 旧密码
5. 服务端执行资产归并

## 19.3 迁移登录接口建议

建议新增一个明确迁移接口，而不是复用普通邮箱登录接口：

```text
POST /v2/api/account/legacy-login
```

请求体建议：

```json
{
  "legacyUsername": "old_user",
  "legacyPassword": "old_password"
}
```

响应体建议：

```json
{
  "migrationRequired": true,
  "emailBound": false,
  "emailVerified": false,
  "legacyUserId": 123,
  "legacyUsername": "old_user",
  "migrationToken": "..."
}
```

说明：

- 这里不直接返回完整 v2 登录态
- 先返回迁移态 token
- 等邮箱绑定和验证完成后，再签发正式 v2 token

## 19.4 迁移态限制

迁移态用户建议限制为：

1. 可以看见绑定邮箱、验证邮箱、迁移说明
2. 不允许进入正式 billing
3. 不允许修改正式账户资料
4. 不允许调用 v2 正式支付能力
5. 只允许完成身份升级动作
