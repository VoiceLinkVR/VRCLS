## 2. 统一后的核心结论

前几轮最容易冲突的说法，统一成下面这组结论，后续编码一律按这一版执行。

### 2.1 用户标识

1. 数据库内部主键仍然是 `user.id`
2. 对外业务主标识统一为 `user_uuid`
3. `email` 是新体系的主登录凭证，不是业务主键
4. `username` 进入兼容期，仅用于：
   - v1 旧接口
   - 老用户迁移登录
   - self-host / 自定义后端密码模式
5. 新注册用户不再手填用户名，不再要求昵称
6. 新注册用户展示名称默认由系统生成，优先使用 `用户 + 短 UUID` 或 `用户 ID`
7. 新接口、token、订单、日志、配额、加油包、授权记录全部逐步切到 `user_uuid`

统一解释：

- `id` 是数据库内部键
- `user_uuid` 是业务唯一身份
- `email` 是 v2 主登录凭证
- `username` 是 legacy 兼容字段

### 2.2 版本边界

1. `v1` 对应旧客户端、旧密码体系、legacy 计费和 self-host 能力
2. `v2` 对应新网站、新控制台、新邮箱体系、新安全模型和新计费能力
3. 新网站默认只接 `v2`
4. 新网站不直接调用 `v1` 发电/支付接口
5. `v1` 是否继续开放由配置控制
6. `v2` 不做“完整兼容旧 API”，只保留受控迁移入口

### 2.3 老用户迁移

1. 老用户可以在新网站使用“旧用户名 + 旧密码”登录一次
2. 登录成功后必须立即进入邮箱绑定/验证流程
3. 完成邮箱绑定后，账户升级为 `v2` 身份体系
4. 升级后主登录方式改为：
   - 邮箱 + 密码
   - 控制台授权登录
5. “邮箱登录后绑定旧账号密码”保留为补充入口，不是主迁移路线

### 2.4 默认测试账户

1. 默认测试账户不是普通用户账号
2. 它是“客户端未登录时使用的匿名兜底身份”
3. 用户不能主动登录这个账户
4. 匿名试用的策略模板归属于默认测试账户
5. 匿名试用的限流和额度统计按 IP 分桶执行
6. 新 v2 下的默认测试账户角色，要替代客户端当前内嵌测试账号的角色
7. 客户端后续不再把默认测试能力表现成一个可见的 `username/password` 账号

### 2.5 资费模型

1. 默认测试档、免费档、正式档、加油包全部配置化
2. 每档金额、每日额度、资源额度、限速都由配置定义
3. 不再依赖固定步长推导每档资源数
4. 旧配置允许继续解析，但只作为 fallback

### 2.6 当前生产现实

1. 当前生产实际仍运行在 `legacy mode`
2. 新计费体系没有正式全量开放
3. 爱发电订单生成与自助激活是 v1 向 v2 过渡研究阶段产物，当前仅在 v2 预览/内测环境使用
4. 旧密码体系在生产仍然有效
5. 新方案必须先承认这一现实，再做分阶段切换

## 3. 当前基线与目标态

### 3.1 v1 稳定基线

稳定基线以服务端 commit `fd03c7df6e15a832dc3fc538fd6c611a36b528cf` 为准。

该基线可确认的事实：

1. 主要路由是：
   - `/api/*`
   - `/manageapi/*`
   - `/ui/*`
2. 当时并没有现在新增的门户、billing、自助迁移等接口族
3. `POST /api/login` 是 v1 登录入口
4. `GET /api/account/status` 是 v1 账户状态入口
5. 这版代码本身没有 `/v1/` 前缀

必须统一的解释：

- `fd03c7d` 是 v1 语义基线
- 最终对外路由应收敛成带版本前缀的目标路径
- 即便源码旧路由没有版本前缀，目标对外路径仍然定义为：
  - `v1 -> /v1/...`
  - `v2 -> /v2/...`

### 3.2 当前服务端实际代码状态

当前服务端工作区已经出现比 `fd03c7d` 更多的路由与能力，包括：

- `src/routers/auth.py`
- `src/routers/portal_api.py`
- `src/routers/user_center.py`
- `src/routers/admin_api.py`
- 邮箱服务与控制台授权相关表结构

这说明当前代码已经开始往 `v2` 方向演进，但对外版本边界、身份主键、迁移口径和计费口径还没有彻底统一。

### 3.3 当前客户端默认测试账户基线

客户端当前仍内嵌了一组 legacy 默认测试账户凭据：

- `D:\git\gitlab\VRCLS-CSharp\01.VRCLS.Core\Models\AppConfig.cs`
  - `DefaultTestUsername = "testuser"`
  - `DefaultTestPassword = "abc123!"`
- `D:\git\gitlab\VRCLS-CSharp\02.VRCLS.Services\Auth\BackendAuthService.cs`
  - `ResetToDefaultAccountAsync()` 会把客户端重置到这组旧凭据并直接登录

这只代表当前客户端的历史实现，不代表目标态设计。

统一解释：

1. `testuser / abc123!` 是当前客户端 legacy fallback
2. 它不是新体系下的正式默认测试账户定义方式
3. 目标态是由服务端 v2 匿名测试能力接管这个角色
4. 客户端后续应把“重置为默认账户”改成“切回匿名测试模式”

### 3.4 目标态

最终目标态不是“在旧接口上继续堆功能”，而是：

1. `v1` 收敛为旧客户端与 self-host 兼容层
2. `v2` 收敛为新官网控制台能力层
3. 新身份体系以 `user_uuid + email` 为核心
4. 老用户通过迁移流转入 v2
5. 爱发电订单生成与自助激活不归入 v1，而是直接归入 v2 billing，并在内测期通过配置控制
6. v2 默认测试账户能力替代客户端内嵌测试账号的角色

## 5. 账户与身份模型

### 5.1 User 表目标字段

`user` 表最终至少应具备以下关键字段：

- `id`
- `user_uuid CHAR(36) UNIQUE NOT NULL`
- `username VARCHAR(...) NULL/UNIQUE`，兼容期保留
- `email VARCHAR(255) NULL`
- `email_verified BOOLEAN NOT NULL DEFAULT 0`
- `display_name VARCHAR(100) NULL`
- `is_default_test_user BOOLEAN NOT NULL DEFAULT 0`
- `identity_version INT NOT NULL DEFAULT 1`
- `is_active BOOLEAN`
- `created_at DATETIME`
- `last_login_at DATETIME`

统一要求：

1. 新用户创建时必须立即生成 `user_uuid`
2. 新用户可以没有 `username`
3. 老用户迁移时保留 `username`
4. 所有新接口响应都应返回 `user_uuid`

### 5.2 新增映射表

为支持老账号迁移与绑定，新增：`user_identity_link`。

建议字段：

- `id`
- `user_uuid`
- `legacy_user_id`
- `legacy_username`
- `legacy_email`
- `link_type`，固定值先支持 `legacy_password_bind`
- `status`
- `linked_at`
- `linked_by_ip`
- `audit_note`

用途：

1. 记录老账号归并关系
2. 记录是否已经绑定过别的用户
3. 为审计和人工排错保留依据

### 5.3 关联表迁移目标

以下表需要补齐 `user_uuid`：

- `account_token`
- `request_log`
- `payment_order`
- `user_session`
- `refresh_token`
- `device_authorization`

迁移规则统一为：

1. 先加可空字段
2. 用 `username -> user_uuid` 回填历史数据
3. 新写入同时写旧字段和新字段
4. 稳定后把查询主键切到 `user_uuid`
5. 最后再考虑是否清理旧字段依赖

## 6. 认证与登录策略

### 6.1 v2 新注册

新注册流程固定为：

1. 输入邮箱
2. 输入密码
3. 输入邮箱验证码
4. 创建账号
5. 自动生成 `user_uuid`
6. 自动生成默认展示名
7. 自动赋予免费档或默认权益

统一口径：

- 不再要求昵称
- 不再要求手填用户名
- 不再允许把账号密码组合作为永久身份标识

### 6.2 v2 主登录方式

v2 主登录方式只有两类：

1. 邮箱 + 密码
2. 控制台授权登录

老用户的旧用户名 + 旧密码只作为迁移入口，不作为 v2 长期主登录方式。

### 6.3 老用户迁移登录

新增迁移接口：

```text
POST /v2/api/account/legacy-login
```

请求体：

```json
{
  "legacyUsername": "old_user",
  "legacyPassword": "old_password"
}
```

响应体建议：

```json
{
  "migrationRequired": true,
  "emailBound": false,
  "emailVerified": false,
  "legacyUserId": 123,
  "legacyUsername": "old_user",
  "migrationToken": "..."
}
```

规则：

1. 这里只返回迁移态凭证，不直接签发完整 v2 登录态
2. 前端收到后只能进入绑定邮箱/验证邮箱流程
3. 完成升级后再签发正式 v2 access token / refresh token

### 6.4 邮箱登录后绑定旧账号

这条能力保留，但定位为补充入口。

入口：

```text
POST /v2/api/account/legacy-link
```

适用场景：

1. 用户已经先用邮箱注册
2. 后续希望把旧账号的历史资产并过来
3. 管理员协助用户完成归并

统一规则：

1. 目标账号始终是当前已登录邮箱账号
2. 旧账号不能反向覆盖邮箱账号的 `user_uuid`、邮箱、密码
3. 旧账号只能绑定一次
4. 若旧账号已绑定别的邮箱账号，则拒绝自动合并
5. 若双方邮箱都已验证且不一致，默认拒绝自动合并，转人工处理

### 6.5 Token 规则

v2 token 统一要求：

```json
{
  "sub": "user_uuid",
  "user_uuid": "...",
  "email": "...",
  "session_type": "portal|device",
  "identity_version": 2
}
```

兼容要求：

1. 服务端在过渡期允许读取旧 token
2. 新签发 token 的 `sub` 必须改为 `user_uuid`
3. 前端本地缓存主键改为 `user_uuid`

### 6.6 控制台授权登录

控制台授权登录在 v2 中继续保留，并作为客户端后续主推荐接入方式。

流程保持：

1. 客户端发起设备授权请求
2. 用户在控制台登录
3. 用户确认授权
4. 客户端轮询换取 token

统一要求：

1. 授权记录与最终 token 返回 `user_uuid`
2. 未登录客户端使用匿名测试能力，不冒用真实账户登录态
3. 客户端本轮只补文档，不改代码

## 7. 邮箱与账户安全

### 7.1 邮箱能力范围

本轮邮箱能力正式纳入服务端主链路，必须覆盖：

1. 注册验证码
2. 找回密码验证码
3. 修改密码验证码
4. 邮箱绑定验证码
5. 邮箱验证

当前已知配置：

- SMTP 主机：`smtp.exmail.qq.com`
- 端口：`465`
- 邮箱账号：`manager@voicelinkvr.top`
- 鉴权信息按现有部署配置使用

### 7.2 修改密码规则

修改密码必须走验证码二次确认，不再只依赖旧密码。

统一流程：

1. 已登录用户请求发送验证码
2. 验证邮箱验证码
3. 设置新密码
4. 旧 session 与 refresh token 失效

### 7.3 找回密码规则

找回密码必须走邮箱验证码。

前端要求：

1. `ResetPassword.vue` 成功后不能只停留在提示页
2. 出现 `Password reset complete` 后自动跳转登录页
3. 推荐 1 到 3 秒内自动跳转，并给出“立即前往登录”按钮

### 7.4 未绑定邮箱的旧用户

旧用户若未绑定邮箱，在以下场景必须提示并引导绑定：

1. 旧账号迁移登录成功后
2. 进入控制台安全页面时
3. 尝试修改密码时
4. 尝试使用完整 v2 能力时

规则：

- 未绑定邮箱的旧用户只能处于迁移态或受限态
- 受限态下不开放完整 v2 计费和安全能力

## 8. 默认测试账户与匿名试用

### 8.1 定位

默认测试账户是匿名能力模板，不是普通用户。

禁止事项：

1. 不能出现在公开登录页
2. 不能出现在普通注册页
3. 不能被用户主动登录
4. 不能作为真实用户的主身份

### 8.2 推荐配置

```env
DEFAULT_TEST_USER_ENABLED=True
DEFAULT_TEST_USER_UUID=00000000-0000-0000-0000-000000000001
DEFAULT_TEST_USER_EMAIL=test@voicelinkvr.top
DEFAULT_TEST_USER_DISPLAY_NAME=Public Test User
DEFAULT_TEST_USER_ACTIVE=True
DEFAULT_TEST_USER_IP_DAILY_QUOTA=800
DEFAULT_TEST_USER_IP_RATE_LIMIT=8/minute
DEFAULT_TEST_USER_RESOURCE_QUOTA=0
```

说明：

1. 邮箱和显示名主要用于后台辨识
2. 不再把默认测试账户当成真实可登录账号
3. 不建议保留对外可用密码

### 8.3 启动自愈逻辑

服务端启动时执行：

1. 检查 `DEFAULT_TEST_USER_UUID` 是否存在
2. 不存在则自动创建
3. 存在则补齐标志位与策略字段
4. 不主动覆盖运营已改的非策略字段
5. 强制标记 `is_default_test_user = true`

### 8.4 流控与额度口径

统一采用“策略归属默认测试账户，统计按 IP 分桶”的口径。

具体要求：

1. 匿名限流键：`anonymous_ip:{client_ip}`
2. 匿名额度键：`anonymous_quota:{client_ip}:{utc_day}`
3. 匿名请求日志字段：
   - `actor_type = anonymous_test`
   - `user_uuid = DEFAULT_TEST_USER_UUID`
   - `rate_limit_scope = ip`
   - `quota_scope = ip`
4. 不允许全站共享一个匿名额度桶
5. 不允许把匿名访问记成真实登录用户流量

### 8.5 与客户端 legacy 默认测试账号的关系

这里必须明确写死，避免后续前后实现打架。

现状：

1. 客户端当前默认测试账号是内嵌的 `testuser / abc123!`
2. 客户端“重置为默认账户”本质上是在登录这个 legacy 测试账号

目标态：

1. v2 默认测试账户能力替代这个角色
2. 客户端未登录时，应落到“匿名测试模式”，而不是展示成一个真实账号
3. 客户端后续不再默认保存 `testuser / abc123!`
4. “重置为默认账户”后续要改名或改语义为：
   - `切换到匿名测试模式`
   - 或 `使用默认试用模式`

过渡期兼容原则：

1. 在客户端代码未改前，可保留 legacy fallback
2. 但所有文档、服务端目标态、前端设计都必须以 v2 匿名测试能力为准
3. self-host 或旧后端兼容场景下，legacy 测试账号是否继续保留由实例配置决定

## 10. 订单、爱发电与 v2 billing 策略

### 10.1 总原则

1. 爱发电订单生成与自助激活不归入 v1
2. 这组能力直接归入 v2 billing
3. 当前仅在 v2 预览/内测环境灰度使用
4. 新网站不直接接 v1 legacy 接口来完成发电或自助激活
5. 如果个别实例需要继续开放当前研究阶段爱发电链路，也应作为 v2 beta 能力开放，而不是回写成 v1 正式能力

### 10.2 新订单写入规则

新订单至少同时写入：

- `user_uuid`
- `username`，兼容期保留
- `email`，可选冗余
- `plan_id`
- `amount`
- `billing_version`

### 10.3 旧订单激活规则

统一按以下顺序查找归属：

1. 先按 `user_uuid`
2. 找不到再按 `legacy_username`
3. 激活成功后尽量回填 `payment_order.user_uuid`

### 10.4 旧账号并入后的订单归并

绑定旧账号时，订单归并规则定死如下：

1. 目标账号始终是当前邮箱账号的 `user_uuid`
2. 旧订单迁移归属到目标 `user_uuid`
3. 历史 `username` 不立即清空，保留审计信息
4. 订单状态保持原值，不因为迁移而改状态
5. 若存在冲突订单，按订单号去重，不做隐式覆盖

### 10.5 加油包归并规则

1. 加油包余额并入目标邮箱账号
2. 不丢弃旧账号已购资源
3. 到期时间取“各自记录独立保留并汇总展示”或“按最晚到期整合”为实现策略二选一，但必须先在代码里定死，不允许运行期随意改
4. 推荐第一版实现为：
   - 余额累计
   - 到期记录独立保留
   - 展示层聚合

### 17.5 状态页

1. 不显示管理员后台状态
2. 不显示内部管理地址
3. 只显示公共服务状态

## 18. 风险与回滚

### 18.1 主要风险

1. 旧库数据质量不一致，可能存在无法直接回填 `user_uuid` 的脏数据
2. 老用户迁移归并时可能出现邮箱冲突和重复绑定
3. 匿名流量改成按 IP 分桶后，NAT 场景会更敏感
4. v1/v2 路由收敛时，前端、网关、服务端可能出现路径不一致
5. 客户端在代码未切换前，仍然会继续使用 legacy 内嵌测试账号

### 18.2 回滚原则

优先回滚配置，不先回滚代码和数据库：

1. 关闭 `API_V2_BILLING_ENABLED`
2. 保留 `API_V2_AUTH_ENABLED`
3. 必要时重新放开 `API_V1_LEGACY_LOGIN_ENABLED`
4. self-host 场景继续走 v1

## 19. 客户端文档要求

本轮客户端不改代码，但后续文档必须明确：

1. 推荐登录方式为控制台授权登录
2. 本地账户主键未来切换为 `user_uuid`
3. 未登录状态使用匿名测试能力，不是登录到真实测试用户
4. 旧用户名/密码只作为 legacy/self-host 兼容方式
5. 账号安全、套餐、订单、邮箱等能力统一由控制台处理
6. 新 v2 默认测试账户能力替代客户端当前内嵌默认测试账号角色
7. 客户端现有 `testuser / abc123!` 仅作为过渡期 legacy fallback 记录，不再作为目标态设计

## 20. 最终结论

最终方案统一为：

1. `v1` 保留旧客户端、self-host、legacy 模式兼容能力
2. `v2` 承接新网站、新控制台、新身份与新计费
3. 对外主身份从 `username` 切到 `user_uuid`
4. 新主登录方式是邮箱 + 密码与控制台授权登录
5. 老用户通过迁移入口完成邮箱绑定并升级到 v2
6. 默认测试账户是匿名能力模板，不允许普通登录
7. 匿名试用的限流和额度都按 IP 控制
8. 套餐、金额、资源额度、加油包全部配置化
9. 公开状态页不再显示管理员后台状态
10. 爱发电订单生成与自助激活直接归入 v2 billing，不再描述为 v1 能力
11. 新 v2 默认测试账户能力替代客户端内嵌 `testuser / abc123!` 的角色
12. 当前生产先承认仍在 `legacy mode`，按阶段推进，不做一步到位切换

按这版文档，服务端、门户和客户端后续接入文档已经统一到同一口径，可以正式进入改代码阶段。
