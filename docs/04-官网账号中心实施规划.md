# VRCLS 官网账号中心实施规划

## 1. 文档目的

这份文档基于 `D:\git\gitlab\VRCLS-CSharp\docs\2026-03-31_账号体系与官网迁移方案.md`，把“账号体系逐步迁到官网”的方向，具体落到 `D:\git\gitlab\vrclswebsite` 这个官网目录。

当前目标不是立刻写业务代码，而是先把官网仓库的职责、技术路线、页面结构、API 依赖和实施顺序定清楚，避免后续边做边改。

---

## 2. 当前现状判断

`vrclswebsite` 现在更接近“静态官网 Demo 仓库”，已经具备：

- 首页展示
- 状态页
- 状态 API Demo 说明
- 适合 GitHub Pages 的纯静态部署方式

但它还不适合直接承接下面这些能力：

- 登录态管理
- 注册 / 找回密码 / 邮箱验证
- 用户中心
- 订单列表
- 发电、续费、升级、降档

原因不是页面数量不够，而是当前结构本质上还是“纯静态宣传站”，缺少：

- 前端路由
- 登录态存储与刷新机制
- API 调用封装
- 表单校验体系
- 受保护页面边界
- 账号中心与支付流程的模块化组织

结论：`vrclswebsite` 可以继续作为官网目录使用，但不能继续只靠当前这套纯 HTML Demo 直接扩展账号中心。

---

## 3. 规划结论

### 3.1 仓库定位

建议把 `D:\git\gitlab\vrclswebsite` 定位为“官网前端仓库”，承接两类内容：

- 对外公开内容：官网首页、下载页、状态页、帮助页
- 登录后内容：账号中心、订单、发电、邮箱绑定、安全设置

### 3.2 技术路线

建议采用“静态展示页 + 前端应用”的双层结构。

推荐方案：

- 保留现有静态首页和状态页能力
- 新增一个前端应用子目录承接账号中心
- 账号中心通过 API 调用 `VoiceLinkServer1` 提供的后端接口

推荐前端技术栈：

- `Vue 3`
- `Vite`
- `TypeScript`
- `Vue Router`
- `Pinia`
- `Axios`

选择这个方案的原因：

- 比继续堆纯 HTML 更适合账号中心这种中等复杂度页面
- 比直接上 SSR 框架更轻，能更快落地
- 最终产物仍然是静态资源，部署成本低
- 后续接登录、订单、邮箱、支付回跳时，结构更稳

如果你后面明确想做成更完整的 Web 产品，再考虑是否升级到 `Nuxt`。当前阶段不建议一开始就上更重的框架。

### 3.3 部署原则

官网和账号中心建议保持同域或至少同主域，避免跨域和登录态复杂化。

推荐形态：

- `/`：官网首页
- `/status`：状态页
- `/download`：下载页
- `/app`：官网登录后应用入口
- `/api`：反向代理到后端服务

如果短期内仍然用 GitHub Pages 托管纯静态首页，那么账号中心部分不要强行塞到 GitHub Pages 体系里，建议单独部署到你自己的站点，再与后端放在同一域名体系下。

建议不要立刻推翻现有目录，而是采用可渐进迁移的结构。

- `auth`
- `account`

## 6. 与原迁移方案的对应关系

官网仓库规划不能脱离原始改造顺序，建议按下面的依赖关系推进。

### 6.1 先决条件：后端 / 客户端 Phase 0

在官网真正接管账号中心前，原方案中的这些动作应优先完成：

- 激活时重新校验已有账号密码
- 新增用户自助修改密码接口
- 客户端去掉“发电顺便改密码”的语义

原因：

- 如果后端边界不先收紧，官网账号中心会建立在错误的密码模型上
- 官网不应该继承“激活等于修改密码”这类历史逻辑

### 6.2 官网 MVP 对应原方案的 Phase 1 和 Phase 2

官网最小上线版建议以这几个能力为主：

- 登录
- 注册
- 修改密码
- 邮箱绑定与验证
- 找回密码
- 用户中心首页
- 订单列表
- 发电入口

### 6.3 官网成熟后再推进 Phase 3

只有当官网用户中心稳定后，客户端才适合进一步收缩为：

- 登录
- 查看权益
- 打开官网

## 7. 官网对后端 API 的依赖清单

官网账号中心最小可用，需要后端至少提供下面这些接口能力。

### 7.1 认证相关

- `POST /api/auth/login`
- `POST /api/auth/logout`
- `POST /api/auth/refresh` 或等效续期接口
- `GET /api/auth/me`

### 7.2 账号安全相关

- `POST /api/account/change-password`
- `POST /api/account/bind-email`
- `POST /api/account/verify-email`
- `POST /api/account/forgot-password`
- `POST /api/account/reset-password`

### 7.3 用户中心相关

- `GET /api/account/profile`
- `GET /api/account/entitlements`
- `GET /api/account/orders`

### 7.4 计费和订单相关

- `GET /api/billing/plans`
- `POST /api/billing/order-intents`
- `GET /api/billing/order-intents/{id}`
- `POST /api/billing/orders/{id}/pay` 或第三方支付跳转接口

### 7.5 关键约束

官网侧不应该继续依赖：

- `custom_id` 里的密码
- 激活阶段修改密码
- 发电流程承担注册账号语义

官网的发电页应只面向“当前已登录用户”，由服务端基于登录态创建 `order_intent_id`。

## 8. 账号中心前端模块规划

### 8.1 登录态模块

需要负责：

- 登录
- 退出登录
- 获取当前用户
- token 续期或 session 校验
- 路由守卫

建议：

- 如果后端允许，优先使用 `HttpOnly Cookie`
- 如果短期内复用现有 Bearer Token，则至少要补齐刷新、过期处理、统一拦截器

### 8.2 表单模块

需要统一处理：

- 注册
- 登录
- 修改密码
- 绑定邮箱
- 找回密码

建议从一开始就统一：

- 字段校验规则
- 错误提示格式
- 提交中状态
- 成功页 / 成功提示

### 8.3 用户中心模块

需要提供：

- 账号总览卡片
- 当前权益卡片
- 套餐信息
- 最近订单
- 安全提醒

### 8.4 订单与发电模块

需要负责：

- 展示套餐
- 创建订单意图
- 跳转支付
- 查询订单状态
- 支付完成回跳展示

关键原则：

- 页面只处理订单，不处理密码
- 支付绑定账号归属，不绑定账号密码语义

### MVP 第一批页面

4. `重置密码页`
5. `账号总览页`
6. `安全设置页`
7. `邮箱绑定页`
8. `订单列表页`
9. `发电页`

### MVP 第一批组件

- 顶部导航
- 登录态头部区域
- 左侧菜单或账号中心页签
- 表单容器
- 订单表格
- 套餐卡片
- 状态徽标
- 空状态组件
- API 错误提示组件

## 10. 实施阶段建议

### 阶段 A：官网仓库准备

目标：

- 明确目录结构
- 选定前端栈
- 搭建 `portal/` 基础工程
- 建立路由、状态管理、API 封装、布局骨架

产出：

- 可运行的前端壳
- 登录页和账号中心空页面

### 阶段 B：账号安全 MVP

目标：

- 接入登录
- 接入当前用户信息
- 接入修改密码
- 接入忘记密码 / 重置密码

产出：

- 可实际登录
- 可完成独立改密
- 可跑通找回密码

### 阶段 C：邮箱与账号中心

目标：

- 接入邮箱绑定
- 接入邮箱验证
- 完成账号总览页
- 完成安全设置页

产出：

- 用户能在官网完成基础账号管理

### 阶段 D：订单与发电迁移

目标：

- 接入套餐展示
- 创建订单意图
- 完成订单列表
- 完成支付回跳页

产出：

- 官网可承担发电和续费主流程

### 阶段 E：客户端收缩

目标：

- 客户端只保留登录和基础权益展示
- 把复杂账号管理入口全部改为跳官网

产出：

- 账号体系职责集中
- 客户端明显减负

## 11. 当前最值得先做的事

如果现在开始正式推进官网，建议下一步不是直接写所有页面，而是按这个顺序启动：

1. 在 `vrclswebsite` 里建立 `portal/` 工程骨架
2. 先把路由、布局、登录态管理跑通
3. 先做 `登录页`、`账号总览页`、`安全设置页`
4. 与后端对齐 `change-password`、`me`、`login` 接口
5. 再进入邮箱和订单能力

这样做的原因是：

- 登录态和基础布局是所有官网业务的底座
- 改密是原迁移方案里最明确、最紧急、最容易验证的官网能力之一
- 邮箱和订单模块对后端依赖更重，应该放在第二步

---

## 12. 风险与注意事项

### 12.1 不要继续复制客户端历史语义

官网不应把下面这些旧逻辑搬过去：

- 发电时修改密码
- 激活时修改密码
- 用订单载荷承载密码语义

### 12.2 不要把账号中心继续做成纯静态拼页

如果继续沿用根目录现有的纯 HTML 方式硬扩：

- 页面复用会迅速失控
- 登录态处理会混乱
- 订单和安全页难维护

### 12.3 不要过早把客户端入口全部下掉

在官网完成注册、登录、找回密码、邮箱绑定之前：

- 客户端仍应保留必要登录能力
- 老用户迁移要有缓冲区

---

## 13. 结论

`D:\git\gitlab\vrclswebsite` 这个目录可以直接作为官网项目的落点，但建议从“静态官网 Demo”升级为“官网静态页 + 账号中心前端应用”的组合结构。

短期内最合理的动作是：

- 保留现有首页和状态页
- 在这个目录下新增 `portal/` 作为官网账号中心应用
- 先围绕登录、改密、账号总览做 MVP
- 等后端邮箱和订单能力准备好后，再逐步承接注册、找回密码、发电和用户中心

这条路线和原始迁移方案是一致的，而且能避免官网一上来就重复客户端已经暴露出来的设计问题。
